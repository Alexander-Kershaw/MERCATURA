# Unity Catalog Storage Architecture

## Purpose

This document explains the Azure and Unity Catalog storage architecture implemented during Phase 0 of Project Meridian.

This predominantly serves as a learning document to demonstrate my understanding and considerations during this initial phase of the project.

It explains:

- why each resource exists
- which security boundary it belongs to
- how Azure Databricks reaches ADLS
- the distinction between authentication and authorisation
- the distinction between managed and external assets
- how Unity Catalog storage objects relate to Azure storage
- what was verified during the bootstrap
- how to diagnose failures across the architecture

---

# 1. Architecture overview

The storage architecture currently contains three conceptual layers:

```text
┌──────────────────────────────────────────┐
│          DATABRICKS GOVERNANCE           │
│                                          │
│ Catalog                                  │
│ Schemas                                  │
│ Tables / Volumes                         │
│ External Locations                       │
│ Storage Credential                       │
└──────────────────────┬───────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────┐
│             AZURE IDENTITY               │
│                                          │
│ Databricks Access Connector              │
│ System-assigned Managed Identity         │
│ Azure RBAC                               │
└──────────────────────┬───────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────┐
│              AZURE STORAGE               │
│                                          │
│ ADLS Gen2                                │
│                                          │
│ managed/                                 │
│ landing/                                 │
└──────────────────────────────────────────┘
```

No single object performs all three responsibilities. I effectively have distinct governance, identity, and storage layers that can interact.

# 3. ADLS Gen2

## 3.1 What ADLS actually is

Azure Data Lake Storage Gen2 is not a completely separate Azure storage product.

It is Azure Blob Storage with the hierarchical namespace capability enabled.

The hierarchical namespace gives object storage a directory-oriented namespace suitable for analytical data workloads. More detail on this is in ADR-0002.

The Project Meridian development account was created with:

```text
StorageV2
Hierarchical namespace enabled
HTTPS required
Minimum TLS 1.2
Anonymous blob access disabled
Shared-key access disabled
```

This means Project Meridian intends to authenticate through Microsoft Entra identities rather than distribute storage account keys.

# 4. Why there are two containers

The development account contains:

```text
managed/
landing/
```

These names describe ownership and lifecycle, not medallion layers.

## 4.1 `managed`

The `managed` container is reserved for data whose storage lifecycle is controlled through Unity Catalog.

Examples will eventually include:

```text
Bronze managed tables
Silver managed tables
Gold managed tables
managed volumes where appropriate
```

Application code should will depend on the internal directory paths generated by Unity Catalog.

For example, engineers should reason about:

```text
mercatura_dev.silver.customer
```

not about whatever hashed cloud storage directory happens to contain that table.

## 4.2 `landing`

The `landing` container represents data delivered by systems outside the analytical platform.

Examples could eventually include:

```text
supplier CSV files
product reference files
legacy exports
acquisition data
partner JSON documents
batch source extracts
```

Those files may be written independently of Databricks.

Their lifecycle therefore remains externally controlled.

The landing area is exposed within Databricks using an external Unity Catalog volume.

---

# 5. Managed versus external does not mean governed versus ungoverned

Both managed and external Unity Catalog assets are governed by Unity Catalog.

The difference is storage lifecycle ownership.

## Managed asset

Unity Catalog manages:

```text
metadata
access control
auditability
lineage
storage location
file lifecycle
```

For example, dropping a managed table removes both its Unity Catalog metadata and its managed files according to the platform lifecycle.

## External asset

Unity Catalog manages:

```text
metadata
Databricks-side access control
auditability
lineage
```

but an external system or administrator manages:

```text
physical storage path
file lifecycle
```

Dropping an external volume does not imply ownership of the underlying files.

This gives Project Meridian the following rule:

```text
If Mercatura Data Platform owns the dataset
        ↓
prefer managed

If another system owns or produces the files
        ↓
consider external
```

# 6. The Databricks Access Connector

The Access Connector is an Azure resource designed to allow Azure Databricks to use Azure managed identities.

I created:

```text
ac-mercatura-dev-uks
```

using a:

```text
system-assigned managed identity
```

This creates two related identifiers.

## Access Connector resource ID

This identifies the Azure resource itself.

Conceptually:

```text
/subscriptions/.../
resourceGroups/.../
providers/Microsoft.Databricks/
accessConnectors/ac-mercatura-dev-uks
```

Unity Catalog references this resource when configuring the storage credential.

## Managed-identity principal ID

This identifies the service principal that Azure RBAC authorises.

Azure role assignments are attached to this identity.

These IDs answer different questions:

```text
What Azure resource represents the connector?
        ↓
Access Connector resource ID

Which Entra principal receives permissions?
        ↓
Managed-identity principal ID
```

# 7. Azure RBAC

Azure RBAC controls what the managed identity can do to Azure resources.

The important baseline role is:

```text
Storage Blob Data Contributor
```

This permits the identity to read and write blob/data-lake content.

Additional permissions were introduced to support later file-event-based ingestion.

The manually bootstrapped environment currently includes:

```text
Storage Queue Data Contributor
Storage Account Contributor
EventGrid EventSubscription Contributor
```

Before Terraform codifies these permissions, the Event Grid role will be checked against current official guidance.

The currently documented automatic file-event model uses:

```text
Storage Blob Data Contributor
Storage Queue Data Contributor
Storage Account Contributor
```

on the relevant storage account and:

```text
EventGrid Data Contributor
```

at the resource-group level.

Infrastructure as Code will encode the reviewed target state.

# 8. Azure management plane versus data plane

Azure has an important distinction between operations on resources and operations on data contained by those resources.

## Management plane

Examples:

```text
create storage account
change networking configuration
create Databricks workspace
create Access Connector
assign Azure roles
```

These operations manipulate Azure resources.

## Data plane

Examples:

```text
create blob container
upload file
read file
delete file
list objects
```

These operations manipulate data within a resource.

This is why having permission to create a storage account did not automatically mean the human developer could create or manipulate blob data.

A temporary:

```text
Storage Blob Data Contributor
```

assignment was therefore granted to myself to create the initial containers.

That assignment was subsequently removed.

---

# 9. Why personal storage access was removed

During bootstrap I temporarily needed direct Azure storage access.

Leaving that access in place would create two paths:

```text
Path A

developer
    ↓
Unity Catalog
    ↓
ADLS


Path B

developer
    ↓
ADLS directly
```

Path B bypasses Databricks governance.

That weakens:

```text
central access control
lineage
auditability
governance guarantees
```

The desired normal operating model is therefore:

```text
developer
    ↓
Unity Catalog
    ↓
governed object
    ↓
ADLS
```

# 10. The Unity Catalog storage credential

I created:

```text
mercatura_dev_storage
```

A storage credential is a Unity Catalog securable object representing credentials used to access cloud object storage.

In this architecture the credential references the Access Connector managed identity.

Conceptually:

```text
mercatura_dev_storage
        │
        ▼
ac-mercatura-dev-uks
        │
        ▼
managed identity
```

The storage credential does not contain:

```text
storage account key
password
client secret
connection string
```

That greatly reduces secret management burdens.

The credential is reusable.

Multiple external locations can refer to the same storage credential when the Azure identity is authorised for those locations.

# 11. External locations

I created two external locations.

## Managed storage location

```text
mercatura_dev_managed
```

Points at:

```text
abfss://managed@stmercaturadev9756f9.dfs.core.windows.net/
```

using:

```text
mercatura_dev_storage
```

This registers the cloud-storage boundary with Unity Catalog.

The `mercatura_dev` catalog uses a subpath beneath this location for managed storage.

## Landing location

```text
mercatura_dev_landing
```

Points at:

```text
abfss://landing@stmercaturadev9756f9.dfs.core.windows.net/
```

using the same storage credential.

An external location can be understood as:

```text
cloud path
    +
authorised cloud identity
    =
governed Unity Catalog storage boundary
```

The storage credential answers:

> Who can Databricks authenticate as?

The external location answers:

> Which cloud path may that identity be used against through this governed object?

# 12. The `mercatura_dev` catalog

I created:

```text
mercatura_dev
```

This is the development environment's primary Unity Catalog boundary.

The architecture intends eventually to use analogous catalogs:

```text
mercatura_dev
mercatura_test
mercatura_prod
```

The development catalog has a managed storage root beneath the `managed` ADLS container.

This means new managed objects can inherit governed storage without each table specifying an explicit cloud path.

A table such as:

```text
mercatura_dev.silver.customer
```

should care about its table identity and schema contract.

It should not need to know its internal Azure filesystem location.

# 13. The landing schema and external volume

The first real schema created was:

```text
mercatura_dev.landing
```

The external volume is:

```text
mercatura_dev.landing.source_files
```

The Databricks-facing path is:

```text
/Volumes/mercatura_dev/landing/source_files/
```

This abstraction means ingestion code can eventually operate against a governed volume path without embedding the physical storage account name throughout the codebase.

Conceptually:

```text
Source system
     │
     ▼
Azure landing files
     │
     ▼
External Location
     │
     ▼
External Volume
     │
     ▼
Databricks ingestion pipeline
```

Later, Auto Loader or another ingestion mechanism can consume this landing area.

# 14. Why Bronze is not the landing container

A common beginner architecture is:

```text
bronze container
silver container
gold container
```

I deliberately not assuming that structure.

The responsibilities are different.

## Landing

Landing answers:

> What file did the external producer deliver?

## Bronze

Bronze will answer:

> What source record did Mercatura ingest and preserve in an auditable, queryable platform representation?

That distinction allows something like:

```text
supplier_prices_20261010.csv
        │
        ▼
landing/source_files/supplier/
        │
        ▼
ingestion
        │
        ▼
mercatura_dev.bronze.supplier_price
```

Landing is a source-file boundary.

Bronze is a data-platform layer.

# 15. Full identity and access chain

The most useful visual for this architecture is:

```text
Databricks user or workload
          │
          │ Unity Catalog privilege
          ▼
Catalog / Schema / Table / Volume
          │
          ▼
External Location
          │
          ▼
Storage Credential
          │
          ▼
Databricks Access Connector
          │
          ▼
Azure Managed Identity
          │
          │ Azure RBAC
          ▼
ADLS Gen2
```

There are therefore at least two independent authorisation systems involved.

## Unity Catalog

Answers:

> Is this Databricks principal allowed to use this governed object?

## Azure RBAC

Answers:

> Is the Azure identity behind Databricks allowed to perform this operation on the storage resource?

Both must succeed.

# 16. Diagnosing access failures

This architecture gives us a useful troubleshooting model.

## User cannot access a table

First investigate:

```text
Unity Catalog permissions
catalog permissions
schema permissions
table permissions
```

Do not immediately change Azure IAM permissions.

## External location validation fails

Investigate:

```text
storage credential
Access Connector reference
managed identity
Azure RBAC
storage networking
cloud path
```

## Volume exists but files cannot be listed

Possible layers include:

```text
volume permission
external-location permission
storage credential
Azure RBAC
ADLS path
```

## Azure CLI cannot manipulate a container

That can be a direct Azure data-plane permission issue and may have nothing to do with Unity Catalog.

This is why the architecture should be diagnosed from the failed layer outward instead of granting increasingly broad permissions until something works.

# 17. Smoke tests and what they proved

Two different tests were deliberately used because they verify different storage models.

## Managed-table smoke test

A temporary schema was created:

```text
mercatura_dev.platform_smoke
```

A managed table was then created and populated.

Successful insertion and querying proved:

```text
catalog configuration
        +
managed storage root
        +
storage credential
        +
managed identity
        +
Azure permissions
        =
functional managed storage
```


## External-volume smoke test

The path:

```text
/Volumes/mercatura_dev/landing/source_files
```

was successfully listed.

This proved:

```text
external volume
        +
external location
        +
storage credential
        +
managed identity
        +
landing-container access
        =
functional governed external storage
```

These are related but distinct proofs.

# 19. Key lessons from this increment

## Lesson 1 — Databricks does not own Azure storage

Azure and Databricks remain separate security systems. Databricks must authenticate to Azure using an Azure identity.

## Lesson 2 — Authentication is not authorisation

The managed identity establishes who Databricks is to Azure. Azure RBAC determines what that identity may do. Unity Catalog separately decides what Databricks users may do.

## Lesson 3 — Managed identity removes secret lifecycle

No application needs to know or rotate an ADLS account key or client secret.

## Lesson 4 — Unity Catalog is more than a metadata catalog

It is part of the security and storage-governance architecture.

## Lesson 5 — Managed versus external expresses ownership

Managed data is platform-owned. External data has an independent storage lifecycle.

## Lesson 6 — Logical and physical architecture should not be confused

Bronze, Silver and Gold do not automatically require three Azure containers.

## Lesson 7 — Least privilege requires removing bootstrap access

Temporary human permissions should not quietly become permanent architecture.

## Lesson 8 — Automation should follow understanding

The manual bootstrap exposed the Azure objects, identity relationships and permissions. Terraform can now encode a reviewed design rather than hiding these concepts.
